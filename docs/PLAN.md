### Модель загроз (2026-10-26)

Що захищаємо: кошти й ключі вбудованого гаманця, паролі/TOTP у vault, приватність перегляду. Від кого: (1) шкідливі сайти й dapp (фішинг, підміна підпису, експлойти рендерера); (2) шкідливі розширення; (3) ланцюг постачання (npm-залежності, GitHub Actions, канал оновлень); (4) відставання Electron/Chromium від патчів; (5) локальне зловмисне ПЗ з доступом до профілю. Поза моделлю: зловмисник з правами адміністратора на ПК власника, фізичний доступ до розблокованої сесії. Наслідок для пріоритетів: найширший клас атак закриває свіжий Electron (S2) і ланцюг постачання (S4); ізоляція підписання (S1) захищає лише від читання пам'яті main-процесу, а не від його повної компрометації (запити на підписання все одно проходять через main), тому вона остання.

- Нові функції — лише ті, якими власник реально користується; невикористовувані підсистеми — кандидати на вимкнення/видалення.
- Без нових мереж, swap і мостів у гаманці.
- **macOS і Linux — experimental** (без CI на цих ОС і без ручної перевірки); основна платформа — Windows.
- Розбиття найбільших модулів (`agent.js` ≈60 КБ, `wallet-solana.js` ≈52 КБ, `solana.js` ≈38 КБ, `app-window.js` ≈37 КБ) — лише разом із тестами, без зміни поведінки.

### 5. Необов'язкове (за бажанням власника)

- Authenticode (Certum OV), winget, Scoop, Chocolatey — не обов'язкові; потрібні лише якщо власник хоче зручну установку для інших. Якщо ні — можна не підтримувати.
- Прибрано з плану: платний/зовнішній аудит гаманця, гранти, bug bounty, маркетинг, спільнота, скрінкасти, «публічні сигнали».

- Не змінювати формат vault, sync або підпису оновлень без шляху міграції й тесту старого формату.

**Гіпотези вузьких місць (гіпотеза, не підтверджено профілюванням):**
1. _Гіпотеза:_ **`Store.flush` синхронний** (`writeSync` + `fsyncSync` + `copyFileSync` у головному процесі): на історії ≈5 МБ — 32–42 мс блокування головного потоку на кожен запис (дебаунс 400 мс), тобто відчутні мікрофризи під час активного серфінгу. Варіант: асинхронний запис/воркер або інкрементальне сховище для історії.
2. _Гіпотеза:_ **Головний процес ≈100 МБ у спокої** через завантаження великих модулів на старті (`context.js` тягне 28 `require`, гаманець/ethers, `agent.js`, Solana), навіть коли гаманець/агент не використовуються. Перевірити `--cpu-prof`/heap snapshot на старті.
3. _Гіпотеза:_ **Стрибок пам'яті 5 → 10 вкладок** (≈39 МБ на вкладку проти ≈23 МБ) — preload `page-preload.js` (інжекції гаманця, vault, WebAuthn) у кожній вкладці та адблок-скриплети; варто перевірити, скільки дає preload на порожній сторінці.
4. _Гіпотеза:_ **`ipcRenderer.sendSync('wallet:init')`** у `page-preload.js` — сам виклик дешевий (0,1 мс), але синхронно блокує рендерер на кожній навігації і стає ризиком, коли головний процес зайнятий (наприклад, `Store.flush` 40 мс або PDF/adblock). Варіант: асинхронна ініціалізація з ледачим провайдером.
5. _Гіпотеза:_ **Інші синхронні `fs` у головному процесі** (`ipc-wallet.js`, `threats.js`, `sync.js`, `updater.js`, `vault.js`) — потенційні блокування при великих файлах (списки загроз до 60 МБ).

### PDF (2026-10-18)

**Зроблено.**
- Вбудований переглядач Chromium у вкладці (пошук, мініатюри, масштаб, поворот, друк). Перевірено в Electron 44: на панелі переглядача є кнопки анотацій («annotate», скасувати/повторити), завантаження й друку; форми AcroForm заповнює сам PDFium. Тому власного переглядача й дублювання анотацій/форм немає: користувач заповнює й анотує у вкладці та зберігає копію кнопкою переглядача.
- Відкриття PDF із «Завантажень» у вкладці (із перевіркою `%PDF-`), «Зберегти сторінку як PDF…» (`printToPDF`).
- **Внутрішня сторінка `w3ir://pdftools` («PDF-інструменти», пункт меню):** злиття кількох PDF у вибраному порядку; розділення за діапазонами (кожен — окремий файл) або по N сторінок у вибрану папку; витяг, видалення й переставляння сторінок («3,1-2», «5-1»); поворот вибраних сторінок; накладання зображення-підпису (PNG/JPEG) на сторінку (7 положень, ширина 5–80 %, з урахуванням `/Rotate`); видалення метаданих; збереження вкладки в PDF з діапазоном сторінок. Бібліотека — `pdf-lib` 1.17.1 (MIT), лише в головному процесі.
- Результат завжди в новий файл; вилучені сторінки не лишаються (створюється новий документ). З результату прибираються дії `/JavaScript`, `/Launch`, `/SubmitForm`, `/ImportData` та `/AA`; звичайні посилання лишаються.

**Обмеження.**
- Закладки (outlines), форми AcroForm і теги доступності при злитті/редагуванні не переносяться (копіюються лише сторінки); для форм — використовуйте переглядач Chromium і його «Зберегти».
- Метадані: прибираються Info, XMP документа й сторінок; вбудовані зображення можуть мати власні EXIF/XMP — їх не чіпаємо.
- Підпис — це зображення на сторінці, а не криптографічний цифровий підпис (PAdES) і не візуальний вибір місця: положення задається пресетом. Інтерактивне перетягування підпису потребує власного переглядача.
- Обробка йде в головному процесі: для файлів у сотні МБ вікно може на кілька секунд «замирати». Лімити: 200 МБ на файл, 400 МБ сумарно, 20 файлів, 5000 сторінок, 200 частин при розділенні. Зашифровані PDF відхиляються (пароль зніміть у джерелі).
- `pdf-lib` 1.17.1 не оновлювався з 2021 року. Ризик обмежений: парсер працює лише з локальними файлами, які користувач сам вибрав, а вхід обмежений за розміром. Альтернатива на майбутнє — `@cantoo/pdf-lib` (форк, активніший), але це нова залежність.
- Діапазон сторінок для «Зберегти сторінку як PDF…»: розділ «Вкладка як PDF» на `w3ir://pdftools` (сторінка відкривається з меню вкладки, яку треба зберегти). Окреме швидке меню «Зберегти сторінку як PDF…» лишається без діапазону (вся сторінка).

**Не робимо зараз: OCR (tesseract.js) — рішення для власника.**
- Оцінка розміру (з npm, розпаковано): `tesseract.js` 7.0.0 (Apache-2.0) ≈1,4 МБ; `tesseract.js-core` ≈30 МБ (кілька wasm-варіантів); мовні дані (tessdata_fast) ≈2–5 МБ на мову, мінімум `eng` + `ukr`; для сканів у PDF потрібне ще перетворення сторінок у зображення — `pdfjs-dist` ≈35 МБ або відрисовка в прихованому вікні Chromium. Разом приблизно +45…70 МБ розпакованого коду і +15…25 МБ до інсталятора (оцінка).
- Ризики: wasm і worker вимагають послаблення CSP (`wasm-unsafe-eval`) або окремого ізольованого процесу; мовні файли мають лежати в збірці (без CDN); зростає поверхня атаки на недовірені зображення; час розпізнавання на CPU — секунди на сторінку.
- Рекомендація: не включати в основну збірку. Якщо потрібно — окремий необов'язковий модуль, що завантажується за згодою користувача з перевіркою підпису/хеша, або використання системного OCR Windows (Windows.Media.Ocr) через окремий помічник. Рішення — за власником.

**Інше, що лишається за рішенням власника.**
1. Пароль/шифрування PDF локально — `pdf-lib` не шифрує; потрібна інша бібліотека.
2. Налаштування «Блокувати JavaScript у PDF» для вбудованого переглядача: Chromium перемикача не дає.
3. Конспект/питання по документу через локальний ШІ-помічник (після рішення про передачу тексту моделі).
4. Обробка великих файлів у `worker_threads`, щоб не блокувати головний процес (зроблено для PDF-інструментів, `src/pdf-worker.js`).
5. Власний переглядач на PDF.js (інтерактивний підпис, анотації з перенесенням у файл) — велика залежність і поверхня атаки.

### Стабільність і безпека (етап 2, виконано)

Зроблено: PDF у воркері; `frame-ancestors`/CSP-заголовки для `w3ir://`; заборона навігації веб-вмісту на `w3ir:`; жест користувача й пауза для зовнішніх схем; лічильник MCP без блокування дійсного токена; мережева перевірка приватних адрес для агента; потокове обмеження списків загроз; монотонний лічильник у sync; обробка `uncaughtException`/`unhandledRejection`, відновлення вкладок і UI, `crash.log`, запис при виході.

Свідомо відкладено:
- **Розширення: показ дозволів і хеш вмісту.** Потрібні розбір `manifest.json`, діалог підтвердження дозволів із перекладами для кожного, зберігання хешу теки та перевірка при запуску (з урахуванням розробницьких оновлень unpacked-розширень). Обсяг — окрема версія (≈2–3 дні з тестами). Поки що `allowFileAccess: false`, а розширення завантажуються лише з шляхів, які додав користувач.
- **Повне закріплення IP для агента** (немає вікна між перевіркою й з'єднанням) — потребує локального проксі; поточний захист: попередній резолв + перевірка адреси після з'єднання.
- **Лічильник MCP «по з'єднанню/IP»:** слухач лише на 127.0.0.1, тож IP завжди однаковий; замість цього обмежуються лише запити без дійсного токена.
- **Синхронізація й старі версії програми:** файл нового формату не читається старими версіями; якщо потрібна сумісність у змішаному парку, лічильник можна вимкнути (рішення власника).
- **M5 (Authenticode)** — за власником. Резервний ключ підпису оновлень уже реалізовано: `update-verify.js` приймає два ключі (`src/update-key.js`).
- Перевірка упакованої збірки (воркер усередині `asar`) і ручні кліки по меню — потрібні на живому застосунку.

## Етап 7. Продуктивність, Ядро та Апаратна Безпека

### 7.1. Перехід на SQLite (FTS5) для історії та закладок — Версія 1.23.0
* **Ціль**: замінити масивні JSON-файли (`history.json`, `bookmarks.json`) на нативний `node:sqlite` (доступний у Node 24 в складі Electron 41).
* **Архітектура за зразком Firefox Places & Chromium**:
  * Таблиця `history` з індексами та розрахунком ваги за алгоритмом **Frecency** (формула: частота візитів × коефіцієнт свіжості за експоненційним спадом).
  * Віртуальна таблиця швидкого повнотекстового пошуку `history_fts USING fts5` з автоматичними тригерами `AFTER INSERT/DELETE`.
  * Зниження навантаження на диск (запис лише змінених рядків, без повної серіалізації JSON на кожен перехід) та миттєва видача підказок в адресному рядку.

### 7.2. Апаратні гаманці (Hardware Wallets via WebHID / WebUSB) — Ledger для EVM експериментально, решта відкладено
> **Стан (2026-10-25):** Ledger для EVM реалізовано в 1.43.5 (`src/ledger.js`, `src/ledger-bridge.js`, власні кадри HID без нових залежностей), перевірено лише на емуляторі за специфікацією; перевірка на справжньому пристрої очікується. Trezor і Ledger для Solana не реалізовано.
* **Чому після ШІ:** підпис транзакцій на пристрої не можна чесно перевірити без фізичного Ledger/Trezor (APDU-обмін, екран пристрою, WebHID у Electron). Реалізація має самоперевірку підписів (адреса відновлюється з підпису до відправки), але вимагає тесту на справжньому пристрої; тому пункт пересунуто за ШІ-частину, яка повністю покривається тестами.
* **Підтримка Ledger та Trezor** для EVM та Solana.
* Використання нативного WebHID через подію сесії Electron `session.on('select-hid-device')` та бібліотеки `@ledgerhq/hw-transport-webhid` / `@trezor/connect-web`.
* Підпис транзакцій безпосередньо на захищеному пристрої без потрапляння закритого ключа в пам'ять процесу.

### 7.3. Локальні ШІ-моделі (Ollama) та Захист від Prompt Injection — Версія 1.24.0
* Підтримка підключення локальних моделей через локальний MCP-сервер W3IR та HTTP API Ollama (`http://localhost:11434`).
* Санітизація веб-сторінок від прихованих інструкцій (патерни `protectai/rebuff` та `llm-guard`: фільтрація `display:none`, прихованих шарів та спроб перезапису системних інструкцій).

### Свідомо не робимо

- **WalletConnect/мобільні гаманці через релеї** — зовнішні сервери-посередники суперечать автономності; повернутися лише за окремим рішенням.
- **Tor-вікно, винагороди за перегляд, власний рушій** (Brave, Ladybird) — окремі великі проєкти без вигоди для наших цілей.
- **Своп/мости в гаманці** — рішення власника (додає ризик підпису й залежності).
- **Копіювання коду GPL-проєктів** (uBlock, Ghostery, Safe) — лише ідеї.
